# Minecraft MCP Debug Harness

A local Fabric 26.3 development client and stdio MCP adapter. Codex can build and launch this repository's Minecraft client with the Minecraft-MCP Fabric mod already loaded, navigate the client UI, work in disposable worlds, inspect performance, and collect bounded logs and crash reports.

The implementation is early-stage. See [docs/architecture.md](docs/architecture.md) for the control contract and current limitations.

## What Codex can do

- Start the isolated development client with `launch_game` using `presetTag: "fresh"` or a named per-instance mod preset, check startup and bridge readiness, and close only its exact managed run with `close_game` (or `stop_game`).
- Inspect available tags and expected mod IDs with `list_mod_presets`; verify what Fabric loaded with `get_game_performance`.
- Load a user-selected, already-built Fabric mod JAR by full path with `load_mod_jar`; it is staged into this MCP instance's own `run/mods/`, loaded on a managed restart, and can be removed with `unload_mod_jar`.
- Send a Minecraft slash command with `run_command` in an MCP-generated disposable single-player world.
- Inspect recent Gradle/Minecraft logs and the latest crash report. Returned text is bounded and redacts local paths, UUIDs, usernames, and token-shaped strings.
- Inspect current Minecraft menus and use revision-bound controls, text fields, and navigation keys. `run_menu_actions` batches up to eight UI steps and returns intermediate results. `open_create_world_menu` opens the real vanilla Create World screen.
- Read client FPS/frame time, JVM heap use, Minecraft/Loader versions, loaded mod versions, and measured integrated-server MSPT/TPS where available.
- Inspect, create, and leave single-player worlds; briefly move, look, and use the held item; capture screenshots.
- Load or edit an existing local save only through an allowlisted disposable copy. `cleanup_generated_world` deletes only exact test worlds and snapshots recorded as created by this mod.

The game controls use a fixed Gradle `runClient` task from this repository. They do not accept arbitrary Gradle tasks or shell commands. The only full path input is the explicitly selected mod JAR; its path is used for that call, copied into this project instance's isolated `run/mods/`, and never saved as a global setting. Slash commands are limited to MCP-generated local single-player worlds. The UI tools refuse destructive controls and refuse to play or edit an original save from the saved-world menu. Use `edit_world_snapshot` to edit a copy.

## Toolchain

Install JDK 25 and Node.js 22 or newer. The generated project targets Minecraft 26.3, Fabric Loader 0.19.5, Fabric API 0.161.0+26.3, Java 25, Fabric Loom `1.18-SNAPSHOT` (resolved as 1.18.2 in the current build), and Gradle 9.7.1. Minecraft 26.1+ is unobfuscated, so the project uses Mojang's official names and has no Yarn mappings dependency. Loom does not create a `remapJar` task for this target; `./gradlew jar` produces the mod JAR directly.

## Build and connect Codex

Build the mod and compile the MCP adapter:

```sh
./gradlew build
cd mcp-server
npm ci
npm run build
```

Register the compiled stdio adapter once from the repository root:

```sh
codex mcp add minecraft-debug -- node /absolute/path/to/Minecraft-MCP/mcp-server/dist/index.js
```

Then restart or reload Codex and use `/mcp` to confirm `minecraft-debug` is connected. Codex starts the Node adapter as its MCP subprocess; **do not run `npm start` as a second server**. The adapter starts Minecraft only when Codex calls `launch_game`.

The first launch may need to download Gradle/Minecraft dependencies and can take several minutes. `launch_game` returns after accepting the request; poll `get_game_process_status` until `bridgeReady` is true. The client uses this project's isolated `run/` game directory, and the Fabric mod creates a local bearer token there on first launch.

To check the local bridge without changing game state:

```sh
cd mcp-server
npm run smoke
```

The smoke check verifies bridge health, unauthenticated-request rejection, and the authenticated status shape. It requires a running client.

To run the opt-in end-to-end UI/world smoke test against the isolated development client:

```sh
cd mcp-server
npm run smoke:client
```

This exercises mouse activation, the allowlisted menu keys, UI text entry, Create World, readiness, movement/look/use, pause/resume, save-to-title, and cleanup. It creates only a uniquely named disposable world and attempts cleanup only after the registry confirms the save was generated by Minecraft-MCP.

To verify the stdio MCP tool layer itself, run `npm run smoke:mcp` from `mcp-server/`. It connects to the running local bridge, batches title-menu actions through `run_menu_actions`, then creates, leaves, and cleans a deterministic generated test world through the MCP tools.

To test the full JAR lifecycle, build the harmless smoke mod and run the process-owning test:

```sh
./gradlew smokeModJar
cd mcp-server
npm run smoke:jar
```

This creates a harmless Fabric probe JAR. If the client is already running outside this stdio adapter, the smoke stages the JAR without closing that client; stop and relaunch it through its owner, then rerun the smoke to verify the mod loaded and unload it. If the adapter owns the client, the smoke exercises the complete managed load, slash command, unload, and exact-run close flow.

If using a separately launched Minecraft profile instead of `launch_game`, set `MINECRAFT_MCP_TOKEN_FILE` to that profile's token file in the Codex server environment. Process management and crash-log collection currently target only this repository's `run/` development client.

## Working with worlds

Use `get_menu_state` and the menu tools to inspect and navigate the title, Create World, and Edit World flows. Click/key/text actions return the resulting menu state so a separate read is usually unnecessary; `run_menu_actions` batches navigation steps. The pause screen allows the safe Back to Game control and Escape; use `leave_test_world` to save and return to title. `open_create_world_menu` opens the vanilla creation form directly; worlds created from that screen are tracked for later cleanup. `create_test_world` is a deterministic shortcut that waits for `worldReady` before returning.

`load_mod_jar` accepts an absolute path on each call and never stores the source path. Build the target project into a Fabric mod JAR first, and use a JAR compatible with this client's Minecraft 26.3 and Fabric Loader 0.19.5. Pass the mod ID from its `fabric.mod.json` as `expectedModId`; the result then checks that ID against Fabric's loaded-mod list. `loaded` is `null` if no expected ID is given, the list is incomplete, or restart is required; the tool only reports `loaded: false` when it checked a complete list and the ID was absent. This workflow does not build or launch the target project's own development profile: it runs the selected JAR inside this repository's isolated development client. Each MCP project keeps its staged target JAR and bridge port under its own isolated `run/` directory, so separate project copies do not share a global JAR selection. If this adapter owns the client, load/unload closes and restarts only that managed run and refuses while a world is open. If another MCP owns the running client, the tool stages or removes the JAR and reports `restartRequired`; that client's owner must restart it. If a load fails, inspect `get_game_process_status`, `get_recent_logs`, and `get_crash_report`. `close_game` can require the exact `runId` returned by `launch_game`.

`launch_game` accepts a `presetTag`. `fresh` launches the base development client with no optional preset mods; a staged target JAR and the Minecraft-MCP bridge remain available. Named presets are configured per project instance in `run/config/minecraft-mcp/mod-presets.json`, and their compatible JARs are placed in `run/mod-library/`. For example:

```json
{
  "presets": {
    "iris-test": [
      { "file": "iris.jar", "modId": "iris" },
      { "file": "sodium.jar", "modId": "sodium" },
      { "file": "modmenu.jar", "modId": "modmenu" }
    ]
  }
}
```

Use `list_mod_presets` to inspect tags, then launch with `presetTag: "iris-test"`; the MCP copies only those listed JARs into the active `run/mods/` directory alongside the staged target mod. `get_game_performance` reports whether each configured preset mod ID was found in Fabric's loaded-mod list. The `run/mod-library/` JARs are kept separate from active mods, so `fresh` omits optional preset mods. Use JARs built for this client's exact Minecraft and Fabric versions. Preset files and staged mods stay inside that project's isolated `run/` directory; a separate project copy has its own presets. Iris itself is a mod JAR; a shader-pack ZIP is a separate asset that must be installed and enabled in Iris.

`list_worlds` lists saves in the isolated `run/` profile by exact folder ID. To test a world stored in another game profile, first copy it into this project's `run/saves/`, then add its exact folder ID to `run/config/minecraft-mcp/world-allowlist.txt`. `load_world_snapshot` opens a disposable copy; `edit_world_snapshot` opens a copy in Minecraft's Edit World menu. The source save is not opened or modified by these tools. Use `open_generated_world` to play a generated snapshot after editing, and `cleanup_generated_world` after returning to a menu to remove a tracked test world or snapshot.

For manual in-world actions, use `get_game_status` to inspect the current state. World creation and snapshot loading wait for `worldReady: true`; movement and item-use calls wait for automatic key release and return final state/position in the same response. Movement lasts at most 40 ticks; item use lasts at most 20 ticks. `leave_test_world` waits until the title screen is active. Screenshots are saved locally under the development profile, with a bounded retention of ten images.

## Safety and limitations

Use the isolated development profile and disposable worlds for debugging. The bridge binds only to `127.0.0.1`, requires a random bearer token for control endpoints, and schedules Minecraft state access on the client thread. A source world must be allowlisted before snapshot or edit-copy operations. Generated copies remain in `run/saves/` until cleaned up.

The current performance reading covers client FPS/frame time, JVM heap, and in-process integrated-server timing. It cannot report authoritative server TPS for a remote server. GameTests, target-project profiles, richer crash correlation, and automatic recovery from hangs remain planned work.
