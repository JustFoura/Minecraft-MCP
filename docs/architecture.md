# Architecture and MCP contract

## Runtime layout

```text
Codex
  └── stdio MCP adapter (mcp-server/)
        ├── fixed Gradle runClient process manager
        │     └── isolated run/ client with Minecraft-MCP Fabric mod
        ├── bounded reads from run/logs and run/crash-reports
        └── authenticated HTTP on 127.0.0.1:8765
              └── Fabric client bridge
                    └── client-thread inspection and actions
```

The MCP adapter derives the project root from its own module location. `launch_game` starts only this repository's Gradle wrapper with the fixed `runClient` task and the repository root as its working directory. The development client uses `run/`, which keeps test saves and logs separate from a normal launcher profile. There are no model-provided task names, shell commands, process arguments, or filesystem paths.

The adapter keeps a bounded tail of Gradle output and monitors the child process. `get_game_process_status` reports launcher exit state and bridge readiness. It reports a ten-minute startup timeout but does not kill the client automatically. `stop_game` sends a graceful interrupt and escalates with bounded waits. When the adapter exits, it signals the process group it started. An already-running unmanaged bridge is detected and a duplicate client is not started.

The mod starts an authenticated HTTP bridge bound only to `127.0.0.1:8765`. It creates a random bearer token under the active game directory's `config/minecraft-mcp/bridge-token.txt`. The MCP process reads the token locally and never includes it in tool inputs or outputs. All Minecraft state reads and writes are dispatched to the client thread with a bounded queue wait; timed-out queued work is discarded.

## Local HTTP API

| Method | Path | Auth | Effect |
|---|---|---|---|
| `GET` | `/health` | No | Liveness only |
| `GET` | `/v1/status` | Bearer | Read screen, world/player presence, world ID, coordinates, and view angles |
| `GET` | `/v1/performance` | Bearer | Read client FPS/frame time, JVM heap, loaded mod versions, and integrated-server metrics |
| `GET` | `/v1/ui` | Bearer | Inspect current screen and up to 128 visible widget controls |
| `POST` | `/v1/ui/open-create-world` | Bearer | Open Minecraft's vanilla Create World UI and mark its result as generated |
| `POST` | `/v1/ui/click` | Bearer | Click a current visible, enabled widget using a screen revision and index |
| `POST` | `/v1/ui/text` | Bearer | Set one current visible text field with at most 128 characters |
| `POST` | `/v1/ui/key` | Bearer | Send one allowlisted navigation key |
| `POST` | `/v1/look` | Bearer | Set yaw/pitch after range validation |
| `POST` | `/v1/move` | Bearer | Hold one movement key for up to 40 ticks, with automatic release |
| `POST` | `/v1/interact` | Bearer | Hold the use key for up to 20 ticks, with automatic release |
| `GET` | `/v1/screenshot` | Bearer | Capture a bounded PNG from the current render target |
| `GET` | `/v1/worlds` | Bearer | List local saves by exact folder ID and report MCP-generated entries |
| `POST` | `/v1/worlds/create-test` | Bearer | Create a uniquely named survival test world with optional seed |
| `POST` | `/v1/worlds/leave` | Bearer | Save and return from local single-player to title screen |
| `POST` | `/v1/worlds/load-snapshot` | Bearer | Require an allowlisted ID, copy it, and open the disposable copy |
| `POST` | `/v1/worlds/edit-snapshot` | Bearer | Copy an allowlisted save and open the copy in Edit World UI |
| `POST` | `/v1/worlds/open-generated` | Bearer | Open an exact test world or snapshot recorded as generated by MCP |
| `POST` | `/v1/worlds/cleanup-generated` | Bearer | Delete one closed test world or snapshot recorded as generated by MCP |

Treat all other paths and methods as unsupported. The Java HTTP executor has a bounded thread pool and queue. The listener and authenticated control surface are local-only.

## Menu and world behavior

`get_menu_state` returns the screen name, translated title, dimensions, visible controls, control labels/types, enabled/focused state, and widget bounds. Each response includes a `screenRevision`. Click, text, and key tools require that revision and increment it after an accepted action, so Codex must inspect the screen again before the next action. Control indexes are bounded and refer only to visible widgets on the current screen.

Menu input goes through the active Minecraft `Screen` and its widgets. The tools do not simulate arbitrary raw mouse coordinates or send arbitrary keyboard codes. Hidden and disabled controls are rejected. Destructive labels, file-browser/import actions, LAN sharing, and confirmation-screen actions are rejected. On `SelectWorldScreen`, only controls labeled create, back, or cancel are allowed, so the original save cannot be opened or changed through generic UI input. Multiplayer, Realms, and pause-screen controls are blocked; Escape remains available to resume or cancel. `press_menu_key` refuses Enter and Space on `SelectWorldScreen`, and neither key can activate a focused protected control on other screens. Use `load_world_snapshot` to play an existing save and `edit_world_snapshot` to open a disposable copy in the vanilla Edit World screen.

`open_create_world_menu` opens Minecraft's vanilla Create World screen. If that flow completes, the integrated server's world folder ID is recorded in the local generated-world registry. `create_test_world` is a direct deterministic shortcut. `list_worlds` lists saves in the active game directory. Loading or editing an existing save requires the exact ID in `config/minecraft-mcp/world-allowlist.txt`; copies are serialized and refuse symlinks, locked saves, unsupported filesystem entries, path escapes, more than 100,000 filesystem entries, or more than 1 GiB of copied data. The source directory is never opened. New snapshots use a unique `mcp_snapshot_*` ID. Cleanup accepts only IDs in the generated-world registry, requires returning to a menu, and verifies the save can be exclusively opened before deletion. World operations have a three-minute MCP request timeout.

## Runtime and diagnostics

`get_game_process_status` reports the managed run ID, elapsed time, Gradle exit code/signal, recent crash-report availability, and whether the in-game bridge is reachable. It reports a startup timeout after ten minutes but does not kill the client automatically.

`get_recent_logs` returns a line- and byte-bounded tail of `run/logs/latest.log` and the managed Gradle output. `get_crash_report` returns the latest crash report up to 48 KiB. Both redact known local roots, player-name fields, UUIDs, and token-shaped values; tool responses include report basenames rather than absolute paths. The client retains at most ten screenshot PNG artifacts under its config directory and deletes failed/oversized captures.

Performance output reports instantaneous client FPS/frame time and JVM heap usage. Integrated-server measurements use 20 tick samples: average tick work in milliseconds and observed start-to-start TPS. These values do not represent remote dedicated-server performance; a remote server would need its own instrumentation.

## Remaining work

GameTests, per-action correlation IDs, automatic hang recovery, and configured target-mod project profiles remain planned. The current launcher intentionally targets Minecraft-MCP itself. To debug another mod, its development profile must later be registered in a separate explicit profile mechanism that loads both the target mod and this bridge; arbitrary external Gradle roots are not accepted by current tools.
