# Architecture and MCP contract

## Runtime layout

```text
Codex
  └── stdio MCP adapter (mcp-server/)
        ├── fixed Gradle runClient process manager
        │     └── isolated run/ client with Minecraft-MCP Fabric mod
        ├── bounded reads from run/logs and run/crash-reports
        └── authenticated HTTP on 127.0.0.1:<per-instance port>
              └── Fabric client bridge
                    └── client-thread inspection and actions
```

The MCP adapter derives the project root from its own module location. `launch_game` starts only this repository's Gradle wrapper with the fixed `runClient` task and the repository root as its working directory. The development client uses `run/`, which keeps test saves, staged mod JARs, bridge token, and bridge port separate from other project copies and normal launcher profiles. Each project root derives a stable preferred loopback port from its own identity, probes the project port range for the next available port when needed, and stores the selected port in that instance's `run/config/minecraft-mcp/bridge-port.txt`. This gives concurrently starting project copies distinct bridge ports without relying on one global port setting. The only filesystem input is the explicit `jarPath` for `load_mod_jar`; it is copied into this instance's `run/mods/` and its source path is not persisted. No model-provided Gradle task names, shell commands, or process arguments are accepted.

The adapter keeps a bounded tail of Gradle output and monitors the child process. `get_game_process_status` reports launcher exit state and bridge readiness. It reports a ten-minute startup timeout but does not kill the client automatically. `close_game` requires the exact managed `runId` when supplied, and both it and `stop_game` signal only this adapter's process group. When the adapter exits, it signals the process group it started. An already-running unmanaged bridge is detected and a duplicate client is not started.

The mod starts an authenticated HTTP bridge bound only to `127.0.0.1` on the port passed to that `runClient` process. The Node adapter stores its selected port and the mod's random bearer token under that project's isolated `run/config/minecraft-mcp/` directory. Each adapter verifies its local token when checking bridge identity, so another project's client is not mistaken for its own. All Minecraft state reads and writes are dispatched to the client thread with a bounded queue wait; timed-out queued work is discarded.

## Local HTTP API

| Method | Path | Auth | Effect |
|---|---|---|---|
| `GET` | `/health` | No | Liveness only |
| `GET` | `/v1/status` | Bearer | Read screen, world/player presence, world ID, coordinates, and view angles |
| `GET` | `/v1/performance` | Bearer | Read client FPS/frame time, JVM heap, loaded mod versions, and integrated-server metrics |
| `GET` | `/v1/ui` | Bearer | Inspect current screen and up to 128 visible widget controls |
| `POST` | `/v1/ui/open-create-world` | Bearer | Open Minecraft's vanilla Create World UI and return its state |
| `POST` | `/v1/ui/click` | Bearer | Send a left-button press/release to one current visible, enabled widget and return the verified resulting state |
| `POST` | `/v1/ui/text` | Bearer | Set one current visible text field with at most 128 characters and return the resulting state |
| `POST` | `/v1/ui/key` | Bearer | Send one allowlisted SDL scancode/keycode pair and return handled/changed state |
| `POST` | `/v1/look` | Bearer | Set yaw/pitch after range validation |
| `POST` | `/v1/move` | Bearer | Hold one movement key for up to 40 ticks, wait for release, and return before/after position |
| `POST` | `/v1/interact` | Bearer | Hold the use key for up to 20 ticks, wait for release, and return final status |
| `POST` | `/v1/command` | Bearer | Send one bounded slash command only to a ready, MCP-generated local single-player world |
| `GET` | `/v1/screenshot` | Bearer | Capture a bounded PNG from the current render target |
| `GET` | `/v1/worlds` | Bearer | List local saves by exact folder ID and report MCP-generated entries |
| `POST` | `/v1/worlds/create-test` | Bearer | Create a uniquely named survival test world with optional seed |
| `POST` | `/v1/worlds/leave` | Bearer | Save and return from local single-player to title screen |
| `POST` | `/v1/worlds/load-snapshot` | Bearer | Require an allowlisted ID, copy it, and open the disposable copy |
| `POST` | `/v1/worlds/edit-snapshot` | Bearer | Copy an allowlisted save and open the copy in Edit World UI |
| `POST` | `/v1/worlds/open-generated` | Bearer | Open an exact test world or snapshot recorded as generated by MCP |
| `POST` | `/v1/worlds/cleanup-generated` | Bearer | Delete one closed test world or snapshot recorded as generated by MCP |

Treat all other paths and methods as unsupported. The Java HTTP executor has a bounded thread pool and queue. The listener and authenticated control surface are local-only.

## Menu and world behavior

`get_menu_state` returns the screen name, translated title, dimensions, visible controls, control labels/types, enabled/focused state, edit-box cursor/selection lengths, and widget bounds. Each response includes a `screenRevision`. Click, text, and key tools require that revision and return the resulting menu state. The MCP adapter also exposes `run_menu_actions`, which resolves unique visible control labels and batches up to eight safe steps while refreshing revisions internally. Control indexes remain bounded and refer only to visible widgets on the current screen.

Menu input goes through the active Minecraft `Screen` and its widgets. A mouse click dispatches both button-down and button-up using SDL's left-button value. Menu keys are allowlisted and constructed with both SDL scancode and logical keycode; navigation is considered handled when focus or visible state changes even if Minecraft returns `false` for focus traversal. The tools do not simulate arbitrary raw mouse coordinates or accept arbitrary keycodes. Hidden and disabled controls are rejected. Destructive labels, file-browser/import actions, LAN sharing, and confirmation-screen actions are rejected. On `SelectWorldScreen`, only controls labeled create, back, or cancel are allowed, so the original save cannot be opened or changed through generic UI input. Multiplayer and Realms controls are blocked. The pause screen allows only Back to Game and Escape; other controls remain blocked. `press_menu_key` refuses Enter and Space on `SelectWorldScreen`, and neither key can activate a focused protected control on other screens. Use `load_world_snapshot` to play an existing save and `edit_world_snapshot` to open a disposable copy in the vanilla Edit World screen.

`open_create_world_menu` opens Minecraft's vanilla Create World screen. The world root is normalized against the active saves directory before its exact folder ID is recorded in the local generated-world registry and returned by status. While an MCP-created world or snapshot is active, `pauseOnLostFocus` is temporarily disabled so an unfocused development window does not trap automation at Pause; the original option is restored on return to a menu. `create_test_world` is a direct deterministic shortcut, and the MCP call waits for the world to become ready. `leave_test_world` disconnects directly to a `TitleScreen` and waits for the synchronous server save/shutdown to finish. `list_worlds` lists saves in the active game directory. Loading or editing an existing save requires the exact ID in `config/minecraft-mcp/world-allowlist.txt`; copies are serialized and refuse symlinks, locked saves, unsupported filesystem entries, path escapes, more than 100,000 filesystem entries, or more than 1 GiB of copied data. The source directory is never opened. New snapshots use a unique `mcp_snapshot_*` ID. Cleanup accepts only IDs in the generated-world registry, requires returning to a menu, and verifies the save can be exclusively opened before deletion. World operations have a three-minute MCP request timeout.

## Runtime and diagnostics

`get_game_process_status` reports the managed run ID, elapsed time, Gradle exit code/signal, recent crash-report availability, and whether the in-game bridge is reachable. It reports a startup timeout after ten minutes but does not kill the client automatically.

`get_recent_logs` returns a line- and byte-bounded tail of `run/logs/latest.log` and the managed Gradle output, capped at 6 KiB per field after redaction. `get_crash_report` returns the latest crash report up to 48 KiB. Both redact known local roots, player-name fields, UUIDs, and token-shaped values; tool responses include report basenames rather than absolute paths. The client retains at most ten screenshot PNG artifacts under its config directory and deletes failed/oversized captures.

## Additional MCP tools

`close_game` targets only the process group launched by this MCP adapter. If the caller supplies a `runId`, it must match the ID returned by `launch_game`; mismatches and unmanaged clients are never signaled. `stop_game` remains an alias for the current adapter's managed run.

`list_mod_presets` returns `fresh` plus the named tags and expected mod IDs from the per-instance preset file.

`launch_game` accepts `presetTag`: `fresh` is the default and selects no optional preset JARs, while a named tag is resolved from `run/config/minecraft-mcp/mod-presets.json`. Each preset lists `{ "file", "modId" }` entries whose JARs are stored in `run/mod-library/`; only the selected list is copied into the active `run/mods/` directory. The selected development target JAR and Minecraft-MCP bridge are independent of the optional preset. The adapter records staged preset filenames and hashes so it can safely replace only its own files on a later launch. `get_game_performance` compares expected preset mod IDs with Fabric's loaded-mod list and reports verified, missing, or incomplete results. Preset config and JARs are per project instance, not a global mod list.

`run_command` accepts a single command with an optional leading slash, up to 256 characters, with no control characters. It routes through Minecraft's client connection only when a local generated test world or disposable snapshot is ready; it never sends commands to multiplayer or ordinary saves.

`load_mod_jar` takes a full absolute path for one local `.jar` on each call. The caller must first build a Fabric mod JAR compatible with this harness's Minecraft 26.3 and Fabric Loader 0.19.5; this tool does not build or launch the selected project's development profile. It stages a bounded JAR as `run/mods/mcp-target.jar` and stores only its basename/hash in the per-project registry, never the source path. When this adapter owns the client, it closes and restarts only that managed run, then checks Fabric's loaded-mod list. Supplying the expected mod ID from the JAR's `fabric.mod.json` verifies that ID. The performance endpoint returns at most 200 mod entries with `loadedModsTruncated` and the full `loadedModCount`; a missing ID is reported as absent only when the list is complete, otherwise `loaded` remains `null`. If no expected ID is supplied, the result is also `loaded: null`. If another adapter owns the running client, it stages the JAR and returns `restartRequired` without signaling that process; `loaded` remains `null` because the JAR was not tested in that still-running client. Both load and unload refuse while a world is open. `unload_mod_jar` removes only the JAR tracked in that registry and restarts without it when safe. Different MCP project copies use distinct `run/` directories and locally selected bridge ports; no global JAR path is configured.

Performance output reports instantaneous client FPS/frame time and JVM heap usage. Integrated-server measurements use 20 tick samples: average tick work in milliseconds and observed start-to-start TPS. These values do not represent remote dedicated-server performance; a remote server would need its own instrumentation.

## Remaining work

GameTests, per-action correlation IDs, automatic hang recovery, and configured target-mod project profiles remain planned. The launcher still uses this repository's fixed `runClient` task; a selected mod JAR is staged into that isolated Fabric profile rather than launching an arbitrary external Gradle project. On load failure, inspect `get_game_process_status`, `get_recent_logs`, and `get_crash_report` for startup diagnostics.
